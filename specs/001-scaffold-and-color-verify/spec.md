## Проблема / зачем

В репозитории нет кода приложения и нет выбранного стека. Нужен минимальный каркас, на котором можно:

1. дальше наращивать продукт (S4 UI, S5 screen-sync) без переписывания BLE-слоя;
2. **сейчас** проверить на реальной ленте, что с компьютера задаётся один общий RGB и выключение.

Это вертикальный срез «развернуть → найти → GATT → цвет», не GUI и не ambilight.

## Пользовательский сценарий

**Дано:** Windows 10/11, адаптер Bluetooth включён, комплект Smartbuy `SBL-RGBW-KIT-75` питается (`12V DC / 2A`), контроллер в эфире под именем `LEDnetWF0200086B1AAC` (так показывает Windows Bluetooth; устаревшая гипотеза имени — `LEDnetWF0200006B1AAC`). Приложение ZENGGE не обязано быть закрытым, но если мешает подключению — его закрывают. UUID и формат кадра — гипотеза из `docs/protocol-notes.md`, не подтверждены.

**Когда:** разработчик ставит зависимости, запускает CLI: scan → connect + перечисление GATT → команда сплошного цвета (красный / зелёный / синий) и off.

**Тогда:**

- scan показывает устройство с именем `LEDnetWF0200086B1AAC` (или префикс `LEDnetWF`);
- после connect в лог/вывод попадает список GATT (services, characteristics, properties);
- лента **визуально** меняет цвет на заданный RGB (вся полоса одним цветом) и гаснет по off;
- фактические UUID, свойства write/notify и **рабочий hex-кадр** RGB/off записываются в `docs/protocol-notes.md` как проверенные (или явно «не совпало»).

## Scope

- Инициализация Python-проекта **внутри `app/`**: зависимости, пакет, CLI, тесты, venv. Корень репозитория остаётся для спек, docs и правил агентов. Инструкция запуска — в корневом README (как войти в `app/` и вызвать CLI).
- Слой BLE (Bleak, Windows backend): scan по имени, connect, disconnect, enumeration GATT.
- Слой протокола: сборка **только** гипотетических кадров питания (on/off) и сплошного RGB из открытого реверса Zengge/LEDnetWF, помеченных как гипотеза до успеха на этом устройстве.
- CLI-команды для проверки: `scan`, `gatt`, `on`, `off`, `color <r> <g> <b>` (значения 0–255).
- Юнит-тесты **без** живого BLE: форма кадра (длина, ожидаемые байты гипотезы), разбор аргументов CLI.
- После успешной проверки на железе — обновить `docs/protocol-notes.md` (чек-лист, UUID, hex).

## Допущения по железу

- Устройство: `LEDnetWF0200086B1AAC` (Windows Bluetooth UI; не `LEDnetWF0200006B1AAC`)
- Тип: analog RGB, один общий цвет; выходы `+ / R / G / B`
- Питание комплекта: `12V DC / 2A`, макс. `24W` — софт мощность не задаёт и не «превышает»
- GATT UUID: гипотеза, пока не сверены — см. `docs/protocol-notes.md`
  - Service `0000FFFF-0000-1000-8000-00805F9B34FB`
  - Write `0000FF01-0000-1000-8000-00805F9B34FB`
  - Notify `0000FF02-0000-1000-8000-00805F9B34FB`
- Если UUID не совпали: CLI печатает фактический список; write **не** уходит в «первый попавшийся» characteristic. Дальнейший write — только в characteristic, выбранную по свойствам write / write-without-response **и** явным логам; неизвестный формат тела — TBD, без выдуманных кадров.
- Write только после enumeration. Notify/CCCD — если без них устройство игнорирует write, включить CCCD; иначе не трогать.
- Кандидаты кадров RGB/on/off — из `docs/protocol-notes.md` и репозиториев 8none1 (`zengge_lednetwf`, `lednetwf_ble`). Первый успешный hex фиксируется в заметках; неуспешный безопасный кадр — тоже документируется, без эскалации в конфиг-команды.

## Критерии успеха

- [x] Приложение ставится на Windows из `app/`: venv, зависимости, CLI вызывается одной командой из корневого README.
- [x] `scan` находит устройство с именем `LEDnetWF0200086B1AAC` (или явно сообщает, что не найдено / Bluetooth недоступен).
- [x] `gatt` подключается и печатает services/characteristics/properties; в выводе видно, совпала ли гипотеза UUID.
- [x] `color` с тремя различными RGB (например 255,0,0 / 0,255,0 / 0,0,255) меняет цвет **всей** ленты; человек это подтверждает глазами.
- [x] `off` гасит ленту (отдельный кадр off **или** RGB `00 00 00` — что сработает, записать в заметки).
- [x] В `docs/protocol-notes.md` после прогона: UUID совпали или нет; hex рабочего RGB; hex off; write vs write-without-response; нужен ли notify/CCCD.
- [x] Юнит-тесты протокола проходят без BLE-адаптера.
- [x] В коде и логах UUID/кадры до подтверждения называются гипотезой; нет API «пиксель N» / «секция».

## Открытые вопросы

- PIN не потребовался. Открытое ZENGGE / удержание линка Windows мешает connect — после disconnect прогон прошёл.
- Какой именно кадр цвета у analog-кита: RGB после `0B 31` **визуально подтверждён** (красная → зелёная → синяя вся полоса). HSV после `0B 3B A1` не пробовали — TBD.
- Игнорирует ли контроллер seq/checksum, как в части реверсов — TBD.
- Имя CLI (`ledsetup` vs модуль `python -m ledsetup`) — на усмотрение реализации, главное — одна команда в README.
- Имя BLE нестабильно — вынесено в спеку `002` (выбор устройства), не в scope 001.
