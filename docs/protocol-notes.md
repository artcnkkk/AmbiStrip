# Заметки по протоколу

Факты железа + прогон CLI на реальном контроллере (2026-08-25). GATT UUID **сверены**. Кадры RGB (`0B 31`) и off (`0B 3B 24`) **визуально подтверждены** пользователем: вся аналоговая полоса красный → зелёный → синий, затем погасла. Не утверждать остальное (CCCD, notify JSON, seq/checksum, HSV, лишние байты).

Вендорское приложение: **ZENGGE**.

## Устройство

Имя в BLE-рекламе **не стабильный идентификатор** (может меняться). Цель в ПО — **адрес**. Имя ниже — last-seen, не константа продукта.

| | |
|--|--|
| Комплект | Smartbuy `SBL-RGBW-KIT-75` |
| Имя BLE (last seen) | `LEDnetWF0200086B1AAC` |
| Адрес (last seen) | `E4:98:BB:6B:1A:AC` |
| RSSI (scan того прогона) | −56 |
| Семейство | Zengge LEDnetWF, analog RGB |
| Выходы | `+ / R / G / B` |
| Цвет | вся лента — один общий цвет |
| Не является | addressable, per-LED, per-section |

Ранее в репозитории фигурировало имя `LEDnetWF0200006B1AAC` (`020000`). В том прогоне Windows Bluetooth UI показывал `LEDnetWF0200086B1AAC` (`020008`) — гипотеза с `020000` **устарела** как «единственное верное имя». Любое точное имя **не** использовать как единственную цель; префикс `LEDnetWF` — только подсказка в scan.

Analog RGB нельзя моделировать как массив пикселей. Команды smear / LED count / chip type (WS2812B и т.п.) из реверсов **addressable**-прошивок на этот кит не посылать без отдельной утверждённой спеки и явной нужды.

Питание: `12V DC / 2A`, макс. `24W`, вход БП `100–240V AC, 50/60Hz`. К протоколу не относится; софт мощность не задаёт.

ZENGGE и/или удержание линка Windows **мешают** connect, пока соединение занято. После закрытия ZENGGE / disconnect в Windows scan+GATT+write прошли без PIN.

## GATT — сверено на этом контроллере

Гипотеза из [8none1/zengge_lednetwf](https://github.com/8none1/zengge_lednetwf) на устройстве с last-seen именем `LEDnetWF0200086B1AAC` **подтверждена** (FFFF / FF01 / FF02).

| Роль | UUID | Факт |
|------|------|------|
| Service | `0000FFFF-0000-1000-8000-00805F9B34FB` | есть |
| Write | `0000FF01-0000-1000-8000-00805F9B34FB` | handle=22, props=`write` + `write-without-response` |
| Notify | `0000FF02-0000-1000-8000-00805F9B34FB` | handle=19, props=`notify` + `read` |

CLI/сессия пишут в FF01 методом **`write-without-response`**, если свойство есть (на этом ките — оба). `write` с response на частоте sync (~10 Гц) на WinRT через какое-то время даёт `characteristic 0016: Unreachable` (handle `0x0016` = 22 = FF01); кадр тот же, меняется только ATT. CCCD на FF02 включался перед write. **Обязателен ли CCCD**, чтобы устройство приняло write — TBD.

Также есть стандартные GAP/GATT (`1800`/`1801`) и **другой** вендорский service `0000FE00-…` с `FF22` (write-without-response, notify, read, handle=13) и `FF11` (write-without-response, handle=16). В них CLI **не** пишет: UUID гипотезы совпали и write в FF01 сработал.
